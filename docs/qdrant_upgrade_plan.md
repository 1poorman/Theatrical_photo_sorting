# Qdrant 改造与对比方案

2026-11-02 开始执行。目标是在容器中提供持久化、可增量更新的在线图像及人脸向量检索，并用同一数据量化与现有 FAISS / Elasticsearch 的差别。

## 选型

采用 Qdrant：本项目以图像/人脸余弦检索和简单元数据过滤为主，独立单容器即可提供增删、过滤、持久化和磁盘向量，不需新增 SQL 业务库。Milvus 更适合需要其分布式架构的规模，但当前项目没有相应容量与运维证据；pgvector 适合已有 PostgreSQL 事务数据集成，本项目没有该基础；现有 ES 继续用于迁移与对照。这里按项目部署与功能需求选择，并非通过未执行的跨数据库基准宣称 Qdrant 全面最快。

## 范围与数据契约

- Qdrant 保存向量和检索元数据；原图、缩略图、任务与人工复核数据保留现有存储。
- 图像按模型、预处理签名和索引数据集隔离，余弦分数保持原义。人脸单独使用 512 维集合，初期精确查询以保持现有身份阈值语义。
- 新图像库分批提取和写入，应用不持有完整向量矩阵。索引路径保留为小型连接清单，旧 FAISS 索引继续可读。
- 增删更新使用稳定 ID、写入确认及模型空间校验；构建失败不能发布半成品。全量重建使用新集合并原子切换清单，旧集合保留以便回退。
- 提供旧 FAISS / ES 的显式迁移工具，不删除源数据，不静默降级至过期索引。FAISS 继续用于离线聚类与精确对照。
- Docker 默认接入 Qdrant；ES 保留为可选旧后端与基准对照。版本固定、数据卷持久化、数据库端口仅在 Compose 内网开放。

## 实施步骤

1. 实现可测试的 Qdrant REST 存储接口、图像检索适配和人脸库适配。
2. 接入现有 HTTP API，保留旧接口及 FAISS 兼容；增加明确的增量写入、删除、过滤和库状态接口。
3. 增加容器部署配置、迁移工具、回归测试与可重复对比脚本。
4. 在真实容器完成接口、增删更新、旧索引迁移、故障隔离、重启恢复及工作台回归。
5. 记录比较结果、配置、硬件、样本来源、局限和采用结论；更新本文件执行状态。

## 冻结的对比口径

- 真实剧照使用同一批 SigLIP2 向量；真实人脸使用同一批 ArcFace 向量。特征提取不混入纯检索耗时。
- 图像比较：旧实现每次读盘、FAISS 常驻精确检索、Qdrant 精确及 HNSW 查询。人脸比较：当前 ES script_score 与 Qdrant 精确查询。
- 记录条目数、维度、写入耗时、查询 p50/p95、吞吐、相对于精确结果的 recall@k 与分数误差、增量可见性。
- 应用内存与数据库进程内存分别报告；磁盘记录实际持久化数据，说明 WAL、预分配及页缓存。不能把数据库占用排除后宣称整体节省内存。
- 真实数据与合成扩容数据分表；合成数据只用于容量和检索算法对比，不代表识别质量。先做真实样本，再做 1 万 / 10 万向量规模测试。
- HNSW 参数及召回率同时披露，小数据可能触发精确扫描，不将其宣传为 ANN 提速。首查与预热查询分开，不声称操作系统冷缓存。
- 不预设 Qdrant 一定比 FAISS 更快或更省磁盘。迁移价值同时评估应用内存上限、增量更新、条件过滤和运行维护。
